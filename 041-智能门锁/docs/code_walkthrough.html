0. 项目全景与工程约束

先立一张"全局地图"。整个固件是四层结构：应用逻辑层（纯 C、可主机测试）→ 板级适配层（把驱动/RTOS 粘起来）→ 驱动层 → RTOS 内核。分层的好处：安全逻辑（鉴权/凭据/状态机）与硬件完全解耦，可以在 PC 上跑单元测试。

1. 启动链路：main() 的每一行

main.c 只有 34 行，是刻意的极简入口。它只做两件事：把一切准备好（smart_lock_app_start()），然后把 CPU 交给调度器（vTaskStartScheduler()）。

int main(void)
{
    if (!smart_lock_app_start()) {   /* ① 准备硬件/配置/队列/任务 */
        for (;;) { }                 /* 失败：死循环等看门狗复位 */
    }
    vTaskStartScheduler();           /* ② 交出 CPU，永不返回 */
    for (;;) { }                     /* 仅"堆不足起不来"才会到这儿 */
}
时钟（72 MHz）由启动文件调用的 SystemInit()（system_stm32f10x.c）配好，main 里不再碰时钟——避免两份初始化互相打架。这是从参考工程继承的纪律。

1.1 smart_lock_app_start() 的四组事（smart_lock_app.c:1808）

  1. board_init() —— 9 类外设全部初始化（见 1.2）。
  2. board_security_load() + security_config_valid() —— 从 W25Q64 读安全配置（A/B 双槽，取 CRC 正确且序号大的），再校验信封。
  3. event_log_init() —— 扫 128 个日志槽，定位"最新一条"，算出下一个可写位置。
  4. 清状态 → lock_controller_init() → set_physical_state()（上电即锁门）→ 建 6 个静态队列 → 建 5 个静态任务 → queue_ui(...,"System ready",true)。

1.2 board_init() 的 9 步（board_port.c:610）

顺序里的三个"必须"（讲这两分钟最出彩）：

  • 第 1 步必须先做 —— PA15/PB3/PB4 复位后默认是 JTAG 功能，不 GPIO_Remap_SWJ_JTAGDisable 释放，键盘的行线就拉不动。
  • 第 3 步必须先 IIC_Init() 再 OLED_Init() —— OLED 走软件 I2C（PB8/PB9）。OLED_Clear() 也不能省：SSD1306 上电显存是随机的，而界面只写第 0/2/4/6 页，第 3 页从没人写，不清屏就会留一条随机噪点带。
  • 第 5 步的"双 Init"—— MCU 复位后 RC522 常首次初始化不成功（上电瞬间芯片内部状态机没起来），MFRC522_Check() 不通就再 MFRC522_Init() 一次（内含 PC14 RST 硬复位脉冲）把它救回来。
⏱ 讲解提示（5 分钟）：从 main 逐行讲到 9 步，重点铺"顺序约束"。先不给结论，问听众"如果先 Init OLED 再 IIC_Init 会怎样"，再揭晓——互动感强。

2. FreeRTOS 任务与队列模型

调度器一起来，5 个任务并发跑。任务之间从不直接调用，一律通过队列通信 —— 这是整个系统能从"一个死循环"演进成"可维护固件"的关键。

2.1 任务表（smart_lock_app.c:1863）

任务优先级栈(字)节拍职责
input_task325610 ms扫键盘/唤醒键/读头 → input_queue
access_task4（最高）384100 ms消费 input/remote → 鉴权决策 → 锁控；管理菜单；每秒 tick（自动落锁/门未关/进 STOP）
network_task276850 msESP8266 AT/MQTT 收下行、发上行
log_task125650 ms写 W25Q64 审计日志、响应回读
ui_task1160阻塞等 ui_queue 刷 OLED
为什么 network 要 768 字？这不是拍脑袋——它是"栈溢出静默死机"事故的产物。esp8266_mqtt_connect() 里光局部变量就有 cmd[192] + token[200] = 392 B，再加上 onenet_calc_token()（base64/HMAC）与 printf 的开销，320 字（1280 B）被用穿。溢出后 FreeRTOS 调 vApplicationStackOverflowHook()（taskDISABLE_INTERRUPTS(); for(;;);）——关中断死循环，什么都不打印。现场特征：串口输出停在 [MQTT] token len=... 中间、xTickCount 冻结、键盘/屏/指纹/刷卡全停，只有断电才好。修复就是把栈加到与参考工程 STK_WIFI=768 对齐。
为什么全静态分配？工程把 configTOTAL_HEAP_SIZE 设成 4 KB（照抄参考工程 16 KB 会在链接时报 L6406E）。既然堆只有 4 KB，就干脆不用动态分配：队列、任务栈、控制块全是 static 数组，xQueueCreateStatic/xTaskCreateStatic 一次成型。好处：启动几乎不可能因内存失败，也彻底杜绝内存碎片。
⏱ 讲解提示（5 分钟）：先画这张数据流图，讲"队列解耦 + 优先级"。然后讲 network 栈 768 的事故——这是"用调试手法反推根因"的经典案例，听众最爱。

3. 输入子系统：键盘 / 唤醒键 / 读头

input_task 每 10 ms 调一次 board_poll_input()（board_port.c:981）。它把三类输入统一成 board_input_event_t 事件：

3.1 键盘：矩阵扫描 + 状态机

key_4x4.c 做行扫描（逐行拉低、读列），keypad_input.c 做去抖与语义化：

  • 25 ms 消抖后产出一个字符键；数字/* 进输入缓冲（回显 *），# = 确认提交。
  • B = 退格删位，C = 取消/退出，A/D = 菜单移动/进入（D → BOARD_MENU_REQUEST）。
  • 无操作超时自动清空输入缓冲。

关键设计：数字键的本地回显由板级层直接写 OLED 第 4 行（ui_render_keypad_entry()），同时发一个 BOARD_KEYPAD_ACTIVITY 事件——这个事件在应用层是空 case，它的唯一作用是刷新 last_activity_at，防止用户输入到一半被"静止 60 s 熄屏"关屏。刻意不 queue_ui，否则会把回显覆盖掉。

3.2 唤醒键 PA8（EXTI8）

/* ISR 里只置一个 volatile 标志，不碰任何 FreeRTOS 对象 */
void board_wake_irq_notify(void) { s_wake_pending = true; }
/* 真正的"唤醒"在 input 任务上下文里翻译成事件 */
if (s_wake_pending) { s_wake_pending = false; event->type = BOARD_TOUCH_WAKE; return true; }

这是嵌入式里最常见的纪律：ISR 越短越好，且绝不调用可能阻塞的 RTOS API（xQueueSendFromISR 也是能避则避）。

3.3 管理菜单模式对输入的接管

当 s_menu_active = true（board_menu_set_active），board_poll_input 走另一条分支：不喂 keypad_input、不轮询读头，每个按键原样上抛为 BOARD_MENU_KEY。这样菜单流程可以"独占"键盘与读头，不会和登录输入打架。

⏱ 讲解提示（4 分钟）：强调"BOARD_KEYPAD_ACTIVITY 是空 case 但有意义"这个细节——体现作者对"回显 vs 状态刷新"边界的思考。

4. 认证与鉴权（核心）

这是全工程最该细讲的地方。handle_board_input()（smart_lock_app.c:1353）是鉴权总入口，一个 switch 分发 7 种鉴权事件。

4.1 凭据不是明文，而是 HMAC 标签

配置里的密码字段是 pin_credential_t（pin_credential.h）：

typedef struct {
    uint8_t tag[SHA1_DIGEST_SIZE];   /* HMAC-SHA1(device_secret, pin) */
    uint8_t pin_length;
    bool    valid;
} pin_credential_t;

也就是说，W25Q64 里从不存明文密码，只存 HMAC(device_secret, PIN) 的标签。校验时对输入重算标签做比较。设备密钥 device_secret[32] 与 TOTP 种子都在同一份安全配置里。

比较用的是常数时间实现（lock_auth.c:3）：

bool lock_constant_time_equal(const uint8_t *l, const uint8_t *r, size_t n) {
    uint8_t difference = 0U;
    for (size_t i = 0U; i < n; ++i) difference |= (uint8_t)(l[i] ^ r[i]);
    return difference == 0U;   /* 全部异或完再判断，不提前 return */
}
为什么？普通 memcmp 会在第一个不同字节处提前返回，攻击者靠测量比较耗时就能逐字节猜出标签（时序侧信道）。这里把差异累积到最后再判，耗时与"第几位不同"无关。

4.2 虚拟前后缀：胁迫码的实现

pin_matches()（lock_auth.c:16）支持 allow_virtual：当输入比存储码长时，滑动窗口在整串里找子串匹配。这样用户被胁迫时，可以输入"胁迫码 + 任意尾巴"（如 654321999）——系统识别为胁迫码，照常开门但静默报警。判决策略里，胁迫码的检查排在业主码之前，所以两者撞号时以胁迫语义优先。

4.3 TOTP 动态口令（RFC 6238）

/* HOTP 动态截断：取末字节低 4 位作偏移，拼 31 位整数再取模 */
offset = digest[SHA1_DIGEST_SIZE - 1U] & 0x0F;
binary = ((digest[offset] & 0x7F) << 24) | (digest[offset+1] << 16) |
         (digest[offset+2] << 8) | digest[offset+3];
return binary % decimal_modulus(digits);

totp_verify(..., time_step=30, digits=6, allowed_window=1) 会校验 [t-1, t, t+1] 三个时间窗（共 ±30 s 容偏）。前提是时间要准——这就是第 7 章要讲 DS3231 的原因：软件时钟一旦断电跳回编译时刻，偏差 >30 s 动态口令就直接失效。

4.4 双因子开锁（second_factor_mode）

模式有 DISABLED / FINGERPRINT_PIN / RFID_PIN 三种。以"指纹+密码"为例：指纹先到 → 不直接开门，而是记下 pending_first_factor = FINGERPRINT、pending_first_factor_until = now + 超时，屏显 Enter PIN；随后密码到 → 校验"第一因子是不是指纹且没过期" → 才开门。这样单凭一个指纹或一个密码都进不去。

case BOARD_AUTH_FINGERPRINT:
    if (second_factor_mode == BOARD_SECOND_FACTOR_FINGERPRINT_PIN) {
        pending_first_factor = LOCK_METHOD_FINGERPRINT;
        pending_first_factor_until = now + SECOND_FACTOR_TIMEOUT_SECONDS;
        queue_ui(controller.state, "Enter PIN", true);
    } else {
        grant_access(LOCK_METHOD_FINGERPRINT, event->user_id, now);
    }

4.5 访客码 / 周期码

两者都是"带时间与次数约束的密码"，模块化在 visitor_credential.c / periodic_credential.c。访客码验证成功后要 board_security_save() 落盘（消耗一次使用次数），落盘成功才开门——注释写得很直白：Never operate the actuator unless state is durable first。访客码刻意绕过双因子，因为访客没有绑定的指纹/卡。

4.6 失败锁定策略

连续失败 maximum_failures（3 次）→ 锁定 lockout_seconds（60 s），期间连菜单入口 D 都被拒（复用同一套 pin_auth_state，避免"连按 D 反复试密码"绕过锁定）。这一逻辑在应用层的 keypad_is_locked/keypad_register_failure，同时复用纯逻辑层 lock_auth_verify_pin()（有主机测试覆盖）。

⏱ 讲解提示（8 分钟）：本章最重。按"明文 → HMAC 标签 → 常数时间 → 虚拟前后缀 → TOTP → 双因子 → 锁定"的顺序讲，每一步都回答"防的是什么攻击"。这一章讲透，安全功底就立住了。

5. 锁控状态机

lock_controller.c 是个 100 行的纯函数状态机，状态只有 4 个，却覆盖了自动落锁、门磁、防撬、锁定全部语义。

case LOCK_CONTROL_AUTH_GRANTED:
case LOCK_CONTROL_REMOTE_UNLOCK:
    controller->state = LOCK_STATE_UNLOCKED;
    controller->unlock_deadline = now + controller->auto_lock_seconds;   /* 自动落锁 */
    break;
case LOCK_CONTROL_TICK:
    if (state == LOCK_STATE_UNLOCKED && unlock_deadline != 0 &&
        now >= unlock_deadline && door_closed) { state = LOCK_STATE_LOCKED; }
    break;

精髓：状态机只算"应该是什么状态"，不碰硬件。真正的动作由 set_physical_state() 落地：

static void set_physical_state(lock_state_t state) {
    board_lock_set(state != LOCK_STATE_UNLOCKED);   /* 舵机 */
    board_alarm_set(state == LOCK_STATE_ALARM);     /* 蜂鸣器 */
}

另外注意 TICK 的自动落锁条件里带了 door_closed：门还开着就不自动落锁，避免把门卡住/夹到人。

⏱ 讲解提示（4 分钟）：把"状态机 vs 硬件动作"分离这点讲清楚——这是可测试性的又一次体现（状态机可以脱机单测）。

6. 存储层：W25Q64 分区与掉电安全

所有"必须活过断电"的东西都在 W25Q64（8 MB SPI Flash）上：配置、卡片表、审计日志。

6.1 为什么是"版本 + 序号 + CRC"的信封

  • 读：两个槽都解析，取"CRC 正确且序号较大"的那个。
  • 写：永远写"当前非活动"的槽（先擦后写），序号 = 活动序号 + 1。

这样在擦/写过程中断电，旧槽仍然完好，配置不会丢——这就是"掉电安全"。而 payload 逐字段编码、不直接 memcpy 结构体，是为了避开编译器填充字节带来的跨平台/跨编译器差异。

一个实战坑：event_type 是按 uint8_t 持久化写进日志的，所以新的事件枚举只能追加在末尾。若在中间插一个值，历史日志的含义会整体错位。

6.2 审计日志环形缓冲（event_log.c）

日志有 128 个固定槽。event_log_init() 开机扫描所有槽，找 sequence 最新的那条，把它后面一槽作为下一个写入点。event_log_append() 擦一槽、写一条（先算 CRC32）。event_log_read_recent(offset) 从最新往回数第 offset 条——这就是菜单"开锁记录"翻页的数据源。

每条记录的完整性靠 event_log_record_valid()：magic 对不对 + CRC32 对不对。sequence_is_newer() 用 (int32_t)(a-b) > 0 处理序号回绕——这是嵌入式里判断"环形序号谁更新"的标准写法。

⏱ 讲解提示（4 分钟）：重点讲 A/B 槽的"先擦非活动槽"策略，配一个"擦到一半拔电"的思维实验。CRC32 和序号回绕是加分细节。

7. 时钟：DS3231 与软时钟回退

时间是这个系统的"安全基石"：TOTP、访客码有效期、云平台 token 的 et、锁定超时全都依赖它。所以时钟必须是真硬件 + 可回退的。

uint64_t board_unix_time(void) {
#if DS3231_USE_SOFT
    return (uint64_t)DS3231_SoftNowUnix();
#else
    DS3231_Time now; DS3231_GetTime(&now); return (uint64_t)DS3231_GetUnix(&now);
#endif
}

当前工程是 DS3231_USE_SOFT = 0（真硬件）。设计上刻意做了双编译分支 + 运行期回落：硬件段拆成 hw_probe/hw_read/hw_write + s_rtc_hw_ok，软时钟段总是编译作为兜底；芯片不回 ACK 就自动回落，系统不会因此死机。

时间语义（务必记牢）：芯片里存 UTC（TOTP / token 的 et / 锁定时效按 UTC 算）；OLED 待机时钟、开锁记录、菜单"改时间"用北京时间（DS3231_LOCAL_TZ_HOURS=8）。开机日志 [RTC] DS3231 online <UTC> 可以一眼确认模块是否在线。

断电还准吗？固件每次只读芯片、绝不回写编译时间（已用"连续两次复位、时间戳自然推进 10 s"验证）。真正的断电保持靠 DS3231 的 VBAT 纽扣电池：电池在位 → 断电继续走时；电池没电 → 冻在断电刻。
⏱ 讲解提示（3 分钟）：强调"UTC 存储 + 本地显示"的分工，以及"软时钟只是兜底、不是正解"。可以把"为什么动态口令会失效"作为悬念抛出来。

8. 显示与 I2C 总线并发锁（一个经典 Bug）

OLED 是 SSD1306（128×64，地址 0x78），走软件 I2C（PB8=SCL / PB9=SDA）。中文字库在 oledfont_cn.h，由 tools/gen_oled_font.py 维护（--check 返回 1 表示缺字）。渲染时每行用 ui_pad_line() 补满 128 px，防止短行右侧留残像；OLED_Clear() 必调（第 3 页没人写）。

8.1 花屏根因：同一总线、多任务、无共同锁

现象：待机页四行文字内容正确，但笔画错乱。根因：OLED(0x78) 与 DS3231(0xD0) 共用 PB8/PB9 一条软件 I2C，却由不同优先级任务访问：
任务优先级I2C 动作
access_task4每轮 board_unix_time() 读 DS3231
input_task3键盘回显写 OLED
network_task2拼 token 的 et 读 DS3231
ui_task1刷整屏 OLED
高优先级任务在低优先级任务"一次 I2C 事务（bit-bang）传到一半"时抢断它 → 两笔事务的 START/数据/STOP 交织 → 从机把半个字节当数据收下 → 随机花屏。oled.c 里已有 s_oled_mtx，但它只挡"OLED 对 OLED"，挡不住 DS3231。

8.2 修复：把锁下沉到"总线事务层"

/* i2c_soft.c：一次事务(START..STOP)不可被抢占 */
static SemaphoreHandle_t s_i2c_mtx;   /* IIC_Init() 里创建为递归互斥量 */
static void i2c_lock(void) {
    if (s_i2c_mtx && xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED)
        xSemaphoreTakeRecursive(s_i2c_mtx, portMAX_DELAY);
}
/* IIC_WriteBytesRaw / IIC_ReadRegs / IIC_WriteReg 入口 i2c_lock()、出口 i2c_unlock() */

用递归锁（因为 oled.c 的 s_oled_mtx 是递归的，会嵌套进入；锁序恒为 s_oled_mtx → s_i2c_mtx，无环不死锁）。FreeRTOS 互斥量有优先级继承，不会优先级反转。

可复用的经验（值得写在白板上）：同一 I2C/SPI 总线上的多个器件，若被不同任务访问，锁必须加在"总线/事务"层，不能只加在某个器件驱动层。否则任务抢占 = 事务交织 = 通信错乱。这个 bug 之所以以前不犯，是因为 DS3231 启用前时钟是软时钟、根本不碰总线。
⏱ 讲解提示（4 分钟）：这是最"有故事"的一章。讲"为什么以前不犯、为什么后犯"，再讲"锁加在哪一层"的一般性结论。

9. 外设驱动：SPI / 串口 / MQTT

9.1 RC522 读卡（SPI1）

  • SPI 模式 0、4.5 MHz（SPI_BaudRatePrescaler_16，保守值）。驱动把 RFCfgReg=0x70（接收增益拉满 48 dB）、TReloadRegL=10（无卡等待 ≈8 ms）。
  • 读到 UID 后主动 MFRC522_Halt() 让卡回 IDLE —— 否则卡停在 ACTIVE 态不再应答 REQA，表现为"卡压在读头上只能读一次"。
  • 两级自愈（本次刚加固）：连续 50 轮（≈5 s）无卡时，① 用 MFRC522_Check() 回读 Init 写过的 TModeReg=0x8D / TPrescalerReg=0x3E 判配置是否丢，丢了立即整片重初始化；② 每 6 次自愈（≈30 s）无条件整片重初始化，兜底"射频/命令状态机卡死"。
    教训：VersionReg(0x37) 是固定硅片 ID（本板恒 0x92），芯片丢了配置也照样读得回，永远不能拿它当健康判据。

9.2 AS608 指纹（USART2）

页号即成员编号：1~48 为成员（48 = 管理员），49 为胁迫指纹。AS608_Identify() 一键识别返回页号与置信分；AS608_DeleteChar() 删模板。指纹模板存在模块内部，所以擦 W25Q64 不会清指纹。

9.3 ESP8266 + MQTT（USART1）

走 AT 指令驱动（esp8266.c）：AT → AT+CWMODE=1 → AT+CWDHCP → AT+CWJAP 连 Wi-Fi → AT+CIPSTART 连 MQTT → 之后用 MqttKit 收发。云平台是 OneNET（mqtts.heclouds.com:1883），token 由 onenet_token.c（HMAC-SHA1 + base64）现算。network_task 收下行命令塞 remote_queue，并把 notify_queue 里的上报发出去。

一个已知的坑：AT 命令的"回显"会被误当成应答。例如 AT+CWJAP? 的期望串若写成 "+CWJAP"，会被命令自身回显命中 → 永远判"已连接"、从不真正 AT+CWJAP。改成 "+CWJAP:"（带冒号）才正确。
⏱ 讲解提示（5 分钟）：三路串口 + 两路 SPI + 一路 I2C 的总线图先讲，再挑 RC522 的"Halt + 两级自愈"和 ESP8266 的"回显陷阱"两个点展开。

11. 一次开锁的完整事件流

把前面所有模块串起来：以"刷指纹开锁"为例，数据在任务/队列/驱动之间的完整旅程。

  1. input_task 400 ms 轮到指纹 → AS608_Identify() 匹配成功 → 发 BOARD_AUTH_FINGERPRINT 进 input_queue。
  2. access_task 收到 → handle_board_input() → 若双因子模式则只记 pending，否则 grant_access()。
  3. grant_access()：board_auth_feedback(true)（蜂鸣+绿灯）→ lock_controller_handle(AUTH_GRANTED)。
  4. 状态机算出 UNLOCKED 并设 unlock_deadline = now + auto_lock_seconds。
  5. set_physical_state() → 舵机转动开锁、告警灯灭。
  6. queue_ui("Access granted") → ui_task 刷 OLED。
  7. queue_audit()：写 log_queue（log_task 落盘 W25Q64）+ notify_queue（network_task 上报 OneNET）。

之后每秒 access_task 发 LOCK_CONTROL_TICK，到点自动落锁。

⏱ 讲解提示（4 分钟）：这张时序图是全篇的收束。讲完它，听众应该能自己复述"一个按键从按下到落地"的完整链路。

12. 调试与工程手法

  • 无头构建：Keil UV4 是 GUI 子系统程序，必须用 GUI 子 shell 调 Start-Process @('-r',proj,'-j0','-o',log) -Wait -PassThru，读 ExitCode。判断有没有真重编只能看日志里有没有 compiling *.c... + Program Size:（hex 的 MD5 无意义，因为 ds3231.c 用 __DATE__/__TIME__）。
  • ST-Link 热插拔读实时寄存器：STM32_Programmer_CLI.exe -c port=SWD mode=hotplug -r32 <addr> <len>。mode=hotplug 必加（不复位不打断，读到真实运行值；len 是字节数）。这是验证"外设到底配没配对/脚到底动不动"的杀手锏。
  • 栈溢出定位：map 查 *_task_stack 地址 → hotplug 读栈底 16 字节。FreeRTOS 用 0xA5A5A5A5 填充，被改写 = 该任务溢出（内容常是返回地址，可反查函数名）。
  • 看门狗：发布版开 SMART_LOCK_ENABLE_IWDG，access_task 每秒 board_watchdog_refresh()；启动失败时 main 里 for(;;) 等它复位。
  • 编码约定：含中文的 .c/.h 必须 UTF-8 带 BOM，否则 AC5 按 CP936 解析报错；字库缺字用 gen_oled_font.py --check 查。
⏱ 讲解提示（3 分钟）：这一章是"工程素养"展示。重点讲"不能只看退出码、要看日志"和"hotplug 读寄存器"这两招。
